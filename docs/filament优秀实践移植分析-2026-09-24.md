# filament 架构与工程实践对 DanQing 的移植价值分析

> 2026-09-24 战略分析（Authored：源码取证报告，非参考移植）。姊妹篇：
> `itwinjs-core-WASM可替换性分析-2026-09-24.md`、`filament-PBR材质接入分析-2026-09-24.md`。
> 所有 file:line 证据来自分析时真实读过的源码（filament / DanQing 仓内）。

## 一、结论摘要

1. DanQing dqRender 已移植 filament RHI 的"形"（Driver 抽象、Handle&lt;T&gt;、OpenGLState 状态缓存 1:1 对齐 OpenGLState.h:187-291），但 filament 引擎前端（filament/src/）的五件"魂器"——FrameGraph 资源生命周期、UboManager 共享 UBO 池、FrameSkipper 背压、TextureCache 瞬态资源缓存、JobSystem——全部缺失。
2. 最高性价比的三项：**TextureCache 瞬态纹理缓存**（直接对症 resize/OIT 事故类资源生命周期问题）、**FrameSkipper**（fence 背压，接口已具备）、**UboManager 共享 UBO**（DanQing 已存在移植后未接线的 rhi::UniformBuffer/DescriptorSetManager，是典型 ported-but-uncalled）。
3. FrameGraph 整套声明式 pass 图**不建议替换** SceneCompositor（itwinjs 管线语义是强契约），但其"资源 devirtualize/destroy 挂到 pass 首末使用者"的生命周期思想值得以最小形态移植。
4. 后处理链（bloom/ACES/SSAO/SSR/DoF/TAA）**不移植**——itwinjs-core WebGL 参考无这些行为，违反 §0 来源铁律会直接改变输出像素。
5. CommandBufferQueue 渲染线程间接层**不移植**——DanQing 的 Driver 是直接虚调用即时模式，符合 itwinjs WebGL 即时语义，引入命令流是负资产。
6. filament 的 WGL 平台层与 DanQing 已实现的设计同构（swapchain 自持 DC、统一 PFD、dummy 窗口、只销毁 headless 窗口），这部分 DanQing 已达标，无需再移植。

## 三、机制要点与 DanQing 接入点

### 1. TextureCache 瞬态资源缓存（P0）

**机制**：所有 FrameGraph 瞬态纹理在"最后一个使用它的 pass"处 destroy（destroyTexture 不进 glDeleteTextures，而是回收到 cache：TextureCache.cpp:239-251），key = (name,target,levels,format,samples,w,h,depth,usage,swizzle)（:183），createTexture 先查缓存命中复用（:186-192）。gc() 每帧 aging：跳帧时清 age&gt;1 的全部、常规每帧最多驱逐 1 项、mCacheMaxAge 老化、且限制 cache 内 distinct age 桶数 ≤3（:253-323）。配套调试器记录驱逐原因辅助参数不匹配排查（:411-454）。
**对症**：DanQing 的 OIT accum/revealage/opaque 快照纹理在每次 resize 时整建置销毁（SceneCompositorImpl.cpp:319-328），且历史上曾因"销毁 GL 程序但编译缓存仍 Success"导致合成 quad 画黑（SceneCompositorImpl.cpp:434-440 注释记录的 2026-09-14 事故）。缓存化后 resize 不再触发 glCreate/Delete 风暴，也降低"句柄悬空"类事故面。
**接入点**：dqRender/src/render/CompositorTextures.{h,cpp} 与 SceneCompositorImpl::preDraw/destroyOitResources——在 rhi::Driver 之上加一层 TransientTextureCache（DanQing 自己的组件，标注 // Authored: mechanism from filament TextureCache.cpp），CompositorTextures::init 改为 cache 取，dispose 改为 cache 还。

### 2. FrameSkipper fence 背压（P0）

**机制**：固定延迟环 mDelayedFences[MAX_FRAME_LATENCY=2]（FrameSkipper.h:47,88-91）。beginFrame 时查最老 fence：未 signal 则丢帧（FrameSkipper.cpp:50-70）；endFrame 时滑窗并新建 fence（:72-86）。注释明确权衡：latency=1 无 CPU/GPU 重叠，=2 全重叠，=3 三管线全重叠（FrameSkipper.h:50-62）。
**对症**：DanQing 有持续渲染（requestNextAnimation）+ 深度缩放连续刷帧场景（ZoomBlackBox 测试即源于真实缩放风暴）；无背压时 CPU 可无限领先 GPU，命令/分配堆积放大卡顿。fence 接口已在 DanQing Driver.h:199-202 就位，是纯消费方逻辑。
**接入点**：dqApp 的 Viewport::renderFrame 第 20 步 drawFrame 前后（CLAUDE.md §10.2 的 24 步管线），或 dqRender/src/render/TargetImpl.cpp 的帧入口。delay 环用 Driver::createFence/getFenceStatus/destroyFence 即可。

### 3. UboManager 共享 UBO 池（P1）

**机制**：全引擎一块 memory-mapped UBO（UboManager.h:153-154），BufferAllocator 子分配 slot、MaterialInstance 按 AllocationId 记偏移；每帧 beginFrame 回收过期 slot、按需重分配（1.5x 增长，:134）；FenceManager 用 fence 跟踪 GPU 在用的 allocation，signal 后回调回收（:54-85）；整帧一次 map/unmap。配合 CPU 侧 UniformBuffer（memcmp dirty：UniformBuffer.h:73-78）与 TypedUniformBuffer::toBufferDescriptor（TypedUniformBuffer.h:53-66）。
**对症**：DanQing 现状是逐 uniform glUniform*（UniformHandle.h:75-212）+ 每帧 `std::unordered_map&lt;std::string, UniformValue&gt;` 字符串查找（ShaderProgramImpl.h:61-122）——每个 draw 命令几十次字符串哈希 + 逐 uniform 派发。并且 rhi/UniformBuffer.cpp 与 DescriptorSetManager 已移植但零调用方（全仓仅自身与测试引用），正是 CLAUDE.md §11.10 警告的 ported-but-uncalled。
**接入点**：先给 DescriptorSetManager 找调用方（dqRender/src/render/ShaderProgramExecutor.cpp 的绑定派发路径），把 ShaderProgramParams 的字符串 map 改为 TypedUniformBuffer 布局结构（偏移常量生成对齐 filament UniformInterfaceBlock 思路）；SceneCompositorImpl::m_frameParams（SceneCompositorImpl.h:221）是最小试点。

### 4. Culler SIMD SoA 剔除（P1）

**机制**：AoS→SoA 输入（cx/cy/cz/ex/ey/ez 分离数组），NEON 路径一次 8 box（Culler.cpp:82-142），标量路径用 `clang loop vectorize_width(4)` pragma（:161-186）；result 是位域，`bit` 参数支持**一次调用并行测多个视锥**（:51,139）——filament 用它同时测主视锥+阴影视锥。球体版本 :189-328。
**对症**：DanQing 剔除是逐 batch 标量循环（RenderCommands.cpp:296），大 tile 场景（imdl 端到端已通）下分支树分支重。
**接入点**：dqRender/src/render/RenderCommands.cpp 的 addBatch 剔除段。注意 DanQing 禁 RTTI/异常但不禁 SIMD intrinsics；MSVC 走 SSE 路径需自写（filament 标量+pragma 路径已给模板）。接入时按 §5 标注 Authored（imodel-native Culler 无对应实现，参考仅 filament）。

### 5. updateBufferObjectUnsynchronized（P1）

**机制**：uniform buffer 更新走 glMapBufferRange(INVALIDATE_RANGE|UNSYNCHRONIZED) 直接 memcpy（OpenGLDriver.cpp:3441-3446），glUnmapBuffer 返回 FALSE（屏幕模式切换期）时 goto retry（:3447-3452），映射失败回退 glBufferSubData（:3453-3456）。整替换时反而用 glBufferData（orphan 语义更快，:3380-3382）。异步版本在 worker 线程 + 共享 context 执行并 glFlush（:3401-3414）。
**对症**：DanQing 每帧大量 uniform/buffer 上传走 glBufferSubData（OpenGLDriver.cpp:310-324），且 TD-15 修复后绑定派发变密集。
**接入点**：dqRender/src/rhi/opengl/OpenGLDriver.cpp 的 updateBufferObject（把 DanQing 已有同名 Unsynchronized 函数从 ARRAY_BUFFER 专属扩展到 UNIFORM_BUFFER，对齐 filament 3416-3462）。

### 6. DebugRegistry + Fgviewer（P2）

**机制**：FDebugRegistry 是类型化属性注册表（bool/int/float/vecN 模板注册，details/DebugRegistry.h:40-64），跨 API 边界用 std::array 桥接 math 类型（:45-59）；DataSource 供外部拉数据。FrameGraph 侧 FgviewerManager 在 compile 时往图里注入 readback pass（FrameGraph.cpp:145-151）并可 export GraphViz（:546-548）。
**对症**：DanQing 现有十余个 DANQING_* env 门控探针（CLAUDE.md §13.1），每次新探针要改代码+重建；DebugRegistry 提供运行时开关面，Fgviewer 式"往渲染序列里注入诊断 pass"正是 DANQING_OIT_DUMP 的通用化。
**接入点**：dqRender/src/render/Diagnostics.h 扩展为注册表（保持 itwinjs Debug 门面作薄封装）。

### 7. JobSystem（P2，条件性）

**机制**：工作窃取 + 无锁引用计数（acq_rel decRef，JobSystem.cpp:293-310）、Dekker 握手防丢唤醒（seq_cst + 双条件变量，:336-352）、per-thread arena 分配 job。渲染命令生成/排序是典型并行负载。
**对症**：DanQing tile 场景（ImdlGraphics 解码、RenderCommands 构建）可并行，但当前单线程。成本高的原因是 dqBase 需新增整个线程池子系统 + DanQing §8.2 引擎 SDK 约束下的线程安全审计。
**结论**：等 Profile 证明命令构建 &gt;5ms/帧再上；当前 P2。

## 四、明确「不值得移植」清单

| 项 | 原因 |
|---|---|
| **CommandBufferQueue/CommandStream + 渲染线程**（CommandBufferQueue.cpp:96-164） | DanQing Driver 是直虚调用即时模式，1:1 符合 itwinjs WebGL 即时语义；itwinjs-core 参考无命令流。引入双线程 + 环形缓冲同步对桌面 CAD 交互渲染是负资产（延迟+复杂度），§0 来源铁律下无参考依据。 |
| **后处理链：bloom（PostProcessManager.cpp:2262）/ACES（ToneMapper.cpp:133-195）/SSAO/SSR/DoF/TAA** | itwinjs-core WebGL 后端无这些 pass，其输出即参考输出。加入任何 tonemap 都会改变像素 = 违反 §0/§5（行为兼容性契约）。DanQing 已有多重采样抗锯齿路径（m_antialiasSamples，SceneCompositorImpl.h:236）对齐 itwinjs RenderBuffer。 |
| **FrameGraph 声明式 pass 图整体替换 SceneCompositor**（FrameGraph.cpp:141-295） | itwinjs SceneCompositor 的 pass 顺序、状态堆栈（BranchStack/ClipStack）、batch 注册是 24 步管线的强契约（CLAUDE.md §10.2），声明式图会把状态副作用（如 pushViewClip/popViewClip 配对）表达扭曲；且 DanQing 事故根因是"资源生命周期管理"而非"pass 编排"。只取 devirtualize/destroy 首末使用者的资源生命周期思想（并入 TextureCache 项）。 |
| **matinfo/matdbg 工具链**（tools/matinfo/src/main.cpp） | filament 材质是二进制包（.filamat），需要包解析工具；DanQing 着色器是源码字符串（ShaderBuilder/DANQING_SHADER_DUMP 已能落盘 .glsl），无对应物。 |
| **Metal/Vulkan/WebGPU 后端** | DanQing 目标是 itwinjs WebGL 行为兼容 + 桌面 GL 平台层，单 GL 后端是定位而非缺口。 |
| **filamat/filabridge 材质系统** | itwinjs 参考用动态 shader 字符串组装（ShaderBuilder 链），替换为离线材质编译体系是与参考决裂的自创架构，§7 禁止。 |
| **glClipControl(LOWER_LEFT, ZERO_TO_ONE)**（OpenGLState.cpp:137-145） | filament 用它把 GL 默认 NDC 改成 [0,1] Z。DanQing 深度约定已随 itwinjs（§12.10 深度反转 saga 修复后 m22 对齐参考），动 clip control 会重新撕开已闭合的伤口。 |
| **Texture::Builder::async 全异步创建体系**（details/Texture.cpp:167,297-313） | 依赖 Engine 级异步模式 + CreationStatus 状态机， DanQing 的 glTF/stb_image 解码路径（TD-14 已做成员级纹理缓存）规模远小；引入半成品异步创建只会复制 filament "creation in progress" 的可不可用状态的复杂度。tile 侧已有 QtTileRequestFetcher（dqApp/src/QtTileRequestFetcher.h:31）异步取流。 |
